Linux Processes and Services: A Practical Guide

Learn how Linux runs programs, how administrators inspect and control processes, and how systemd manages background services.

Beginner to Intermediate Linux Administration 12–15 min read

1. Introduction

When you open a terminal, run a command, connect to a server or start a web application, Linux creates and manages processes. Many important programs continue running in the background without an administrator interacting with them directly. These long-running programs are commonly managed as services.

System administrators need to identify resource-heavy processes, stop unresponsive applications safely, ensure required services start at boot, and investigate failures through logs.

Lab safety: Practise in a Linux virtual machine. Do not terminate unfamiliar processes or change services on a production system without understanding their purpose and impact.

2. What Is a Linux Process?

A process is an instance of a running program. Each process has a Process ID (PID), an owner, a state and resource usage such as CPU time and memory. A process may create child processes, forming a parent-child relationship.

  • PID: unique process identifier while that process exists.
  • PPID: parent process ID.
  • UID: user identity under which the process runs.
  • TTY: associated terminal, if any.
  • State: indicates whether a process is running, sleeping, stopped or in another state.

Common process states shown by tools include running, interruptible sleep, uninterruptible sleep, stopped and zombie. A zombie is an exited process whose parent has not yet collected its exit status; it is not a process that is still executing normally.

Linux exposes process information through the /proc virtual filesystem. For example, /proc/1 contains information about the process with PID 1 on the current system.

3. Inspect Running Processes

Start by learning to observe the system before attempting to change anything.

CommandPurpose
psShow processes associated with the current terminal.
ps auxShow a detailed snapshot of processes across the system.
ps -efDisplay processes in a full-format listing.
ps -p 1234 -fInspect a particular PID (replace 1234).
topDisplay live process and resource information.
pgrep sshdFind process IDs matching a process name.
pidof sshdFind PIDs for a program when supported.
free -hSummarize memory usage.
uptimeShow uptime and system load averages.

In top, observe CPU and memory usage, process IDs, owners and load averages. Press q to quit. Some distributions provide htop, an interactive alternative that may need to be installed separately.

Tip: ps aux and ps -ef are two common formats. Their columns and option styles differ; do not assume the output is identical.

4. Control Processes and Signals

Linux uses signals to communicate with processes. The kill command sends a signal to a PID; despite its name, it does not always terminate a process.

SignalMeaningTypical use
SIGTERM (15)Request a process to terminate.Preferred first attempt for a process you need to stop.
SIGKILL (9)Force termination; cannot be caught or ignored.Last resort when a process will not exit normally.
SIGHUP (1)Hangup signal, with behavior defined by the application.Some daemons use it to reload configuration.
SIGINT (2)Interrupt from the keyboard.Often generated by Ctrl+C in a terminal.

kill -TERM 1234 — request graceful termination of PID 1234.

kill -KILL 1234 — force termination only if necessary.

pgrep -a nginx — find matching processes and show their command lines.

Always verify the PID and command before sending a signal. Avoid using broad commands such as killall or force-killing processes without confirming what they do. A service-managed process is usually better controlled through its service manager rather than by killing its PID directly.

5. Foreground and Background Jobs

A command launched from a terminal normally runs in the foreground, keeping that shell occupied until it completes. Add & to start a command in the background.

sleep 300 — run in the foreground.

sleep 300 & — start in the background.

jobs — list jobs started by the current shell.

Ctrl+Z — suspend the foreground job.

bg — continue a suspended job in the background.

fg — bring a background job to the foreground.

Shell jobs are tied to the shell session. Closing a terminal can affect them. For long-running production workloads, use a service manager such as systemd, a terminal multiplexer, or another suitable process supervisor instead of relying on a shell background job.

6. Introduction to systemd

systemd is an init system and service manager used by many modern Linux distributions. It starts and supervises system components and can manage services, mounts, timers, sockets and other unit types.

A unit is a resource managed by systemd. A service unit typically describes how a background program is started, stopped and supervised. Unit files may be supplied by packages or created by administrators.

  • Active: describes the unit's current high-level state.
  • Enabled: indicates that the unit is configured to start automatically through its installation links.
  • Disabled: means it is not enabled for automatic startup in that way.
  • Failed: indicates that systemd recorded a failure state.
Important: Enabled does not mean currently running, and running does not necessarily mean enabled at boot. Runtime state and boot-start configuration are separate concepts.

7. Manage Services with systemctl

The systemctl command is the main command-line tool for inspecting and controlling systemd units.

CommandPurpose
systemctl status sshInspect the SSH service (service name varies by distribution).
systemctl start nginxStart a service now.
systemctl stop nginxStop a service now.
systemctl restart nginxStop and start a service.
systemctl reload nginxAsk a service to reload configuration, if it supports reload.
systemctl enable nginxConfigure the service to start automatically at boot.
systemctl disable nginxRemove that automatic-start configuration.
systemctl enable --now nginxEnable and start the service.
systemctl is-active nginxCheck whether the service is active.
systemctl is-enabled nginxCheck whether it is enabled.
systemctl list-units --type=serviceList service units currently loaded.
systemctl list-unit-files --type=serviceList installed service unit files and their enablement states.

Use the correct service name for your distribution. For example, the OpenSSH server unit is commonly named ssh on Debian/Ubuntu and sshd on Fedora/RHEL-family systems. A service may not be installed by default.

After editing a systemd unit file, run sudo systemctl daemon-reload so systemd rereads unit definitions. This command does not itself restart the application; restart the affected service separately when required.

8. Read Service Logs with journalctl

On systems using systemd's journal, journalctl helps administrators investigate startup errors, crashes and other service events.

journalctl -u nginx — show journal entries for a service.

journalctl -u nginx -b — show entries from the current boot.

journalctl -u nginx -f — follow new entries as they arrive.

journalctl -p err -b — show error-priority entries from this boot.

journalctl --since "1 hour ago" — filter entries by time.

Use q to exit the journal pager. Access to some logs may require elevated privileges or membership in an appropriate system group. Journal persistence and retention depend on system configuration.

9. A Practical Service Troubleshooting Workflow

  1. Check the state: run systemctl status service-name.
  2. Read recent logs: use journalctl -u service-name -b.
  3. Check the process: use pgrep -a process-name or ps.
  4. Check resources: inspect CPU and memory with top and free -h.
  5. Check configuration: use the application's own configuration-test command where available.
  6. Check dependencies and ports: confirm required files, permissions, network access and listening ports.
  7. Make one controlled change: restart or reload only after identifying a likely cause.
  8. Verify: check service status, logs and application behavior again.

A service that exits immediately may have a configuration error, missing file, permission problem, occupied port or unavailable dependency. The log message is usually more useful than repeatedly restarting the service.

10. Hands-on Lab: Inspect and Manage a Service

Use a disposable Debian/Ubuntu or Fedora/RHEL-family virtual machine with systemd. This lab uses Nginx as an example web service. Install it only if you are comfortable adding packages to your lab VM.

Debian or Ubuntu

sudo apt update

sudo apt install nginx

Fedora or RHEL-family systems

sudo dnf install nginx

Manage and verify the service

sudo systemctl enable --now nginx

systemctl status nginx

systemctl is-active nginx

ps -ef | grep '[n]ginx'

sudo journalctl -u nginx -b --no-pager

curl -I http://localhost

sudo systemctl restart nginx

systemctl status nginx

Answer these questions after the lab:

  1. What is the difference between a PID and a PPID?
  2. How is a process different from a systemd service?
  3. What is the difference between start and enable?
  4. Why should you inspect logs before repeatedly restarting a failed service?
  5. What does journalctl -u nginx -b show?

When finished, you can stop the service with sudo systemctl stop nginx. Disable boot startup with sudo systemctl disable nginx if you no longer want it to start automatically. Uninstall it only if you no longer need it.

11. Linux Process and Service Administration Checklist

  • Identify a process and verify its PID before sending signals.
  • Prefer graceful termination with SIGTERM before considering SIGKILL.
  • Use systemctl to manage services supervised by systemd.
  • Enable only services required by the system's role.
  • Review service logs and configuration before making changes.
  • Run services with the least privileges they need.
  • Keep packages and service configurations maintained according to policy.
  • Test service changes in a lab before applying them to production.

Frequently Asked Questions

What is the difference between a process and a service?

A process is a running instance of a program. A service is a background function or application that is commonly managed by a service manager such as systemd. A service is implemented by one or more processes.

Does systemctl start also enable a service at boot?

No. Start changes the current runtime state. Enable configures automatic startup through systemd's unit relationships. Use systemctl enable --now when both actions are intended.

Should I always use kill -9?

No. SIGKILL prevents the process from handling the termination request or performing normal cleanup. Try a graceful SIGTERM first and investigate why the process does not exit.

What is the difference between restart and reload?

Restart stops and starts the service. Reload asks the application to reread its configuration without a full stop/start, when the application and its unit support that operation.

Conclusion

Understanding processes and services is essential for Linux system administration. With ps, top, signals, systemctl and journalctl, administrators can inspect workloads, manage background services and investigate failures methodically. Practise in a virtual machine before making changes to real systems.
