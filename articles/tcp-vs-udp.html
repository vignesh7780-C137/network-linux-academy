1. What Is the Transport Layer?

The transport layer is responsible for communication between applications running on different devices. It provides services that allow application processes to exchange data across a network.

In the TCP/IP model, TCP and UDP operate at the transport layer. In the OSI model, they are commonly associated with Layer 4.

Consider opening a website. Your computer communicates with a remote server, but the communication is not simply between two IP addresses. Multiple applications may be communicating simultaneously.

Transport protocols use port numbers to help identify the application endpoints involved in communication.

Application Layer HTTP, DNS, SSH, DHCP
↓
Transport Layer TCP / UDP
↓
Internet Layer IPv4 / IPv6
↓
Network Access Ethernet / Wi-Fi

Why do we need TCP and UDP?

IP provides addressing and packet delivery across interconnected networks. However, IP itself does not provide application-level reliable, ordered delivery.

Applications often need additional transport services. TCP and UDP offer two different approaches:

  • TCP: Provides a reliable, ordered byte stream.
  • UDP: Provides a lightweight datagram service without TCP's built-in connection and reliability mechanisms.

2. What Is TCP?

TCP (Transmission Control Protocol) is a connection-oriented transport protocol that provides reliable, ordered delivery of a byte stream between applications.

Before normal application data is exchanged, TCP establishes a connection between the communicating endpoints. It then uses sequence numbers, acknowledgments, retransmission, flow control, and congestion control to manage communication.

Important characteristics of TCP

  • Connection-oriented: Establishes connection state before normal data transfer.
  • Reliable delivery: Uses acknowledgments and retransmissions to recover from loss.
  • Ordered delivery: Presents received data to the application in sequence.
  • Full-duplex: Supports data transfer in both directions.
  • Flow control: Uses a receive window to help prevent a sender from overwhelming the receiver.
  • Congestion control: Adjusts sending behavior to respond to network congestion.
  • Byte-stream service: Applications send and receive a stream of bytes rather than independent message boundaries.
Important concept

TCP provides a byte stream. It does not preserve application write boundaries as separate messages. If an application needs message boundaries, it must define them within the stream.

3. What Is UDP?

UDP (User Datagram Protocol) is a connectionless transport protocol that allows applications to send individual datagrams.

Unlike TCP, UDP does not establish a transport connection through a handshake before sending application data.

UDP also does not provide built-in retransmission, sequencing, or flow and congestion control equivalent to TCP. Applications that need such features must implement or use additional mechanisms.

Important characteristics of UDP

  • Connectionless: No TCP-style connection establishment.
  • Low protocol overhead: Uses a compact 8-byte header.
  • Datagram-based: Preserves individual message boundaries.
  • No built-in retransmission: Lost datagrams are not automatically recovered by UDP.
  • No built-in ordering: Datagrams may arrive out of order.
  • Application flexibility: Applications can design their own reliability or timing mechanisms when needed.
Does UDP guarantee delivery?

No. UDP provides no guarantee that a datagram will arrive, arrive only once, or arrive in order. It offers a lightweight transport service and leaves additional behavior to the application.

Which one is faster?

UDP generally has less transport-layer overhead because it does not perform TCP's connection establishment, acknowledgments, and retransmission procedures.

However, it is inaccurate to say UDP is always faster in every application. Actual performance depends on network conditions, application design, congestion, packet size, and the protocol built on top of UDP.

5. How TCP Establishes a Connection

TCP normally establishes a connection using a process called the three-way handshake. It uses three TCP segments to synchronize connection state between the endpoints.

Step 1: SYN

The client sends a TCP segment with the SYN flag set. It proposes an initial sequence number and requests connection establishment.

Step 2: SYN-ACK

The server responds with SYN and ACK flags set. It acknowledges the client's SYN and provides its own initial sequence number.

Step 3: ACK

The client sends an acknowledgment. The connection is now established and application data can be exchanged.

CLIENT SERVER
SYN ──────────────→
←────────────── SYN + ACK
ACK ──────────────→
TCP connection established

Why does TCP need a handshake?

The handshake allows both endpoints to synchronize connection state and initial sequence numbers. It also confirms that the other endpoint is participating in the connection establishment process.

This handshake does not mean that TCP has verified the identity of the remote application or authenticated the user. Authentication and encryption are separate concerns, commonly handled by protocols such as TLS.

How does TCP close a connection?

TCP commonly uses FIN and ACK segments to close a connection gracefully. Because TCP is full-duplex, each direction can be closed independently.

A typical graceful close involves four segments: one endpoint sends FIN, the other acknowledges it, and later sends its own FIN, which is acknowledged. RST can be used to reset a connection instead.

6. How TCP Provides Reliable Communication

TCP uses multiple mechanisms to provide reliable and ordered delivery.

6.1 Sequence numbers

TCP assigns sequence numbers to bytes in the transmitted stream. These numbers help the receiver identify the position of data and detect missing or duplicate segments.

6.2 Acknowledgments

The receiver sends acknowledgment information to indicate the next byte it expects to receive. TCP acknowledgments are generally cumulative.

6.3 Retransmission

If data is not acknowledged within the relevant retransmission timeout, TCP can retransmit it. TCP also uses other loss-recovery mechanisms, such as fast retransmit, depending on the situation.

6.4 Flow control

TCP uses a receive window to communicate how much additional data the receiver is currently willing to accept. This helps protect a receiver from being overwhelmed by incoming data.

6.5 Congestion control

TCP also manages the amount of data sent into the network to respond to congestion. Congestion control helps prevent excessive traffic from overwhelming network paths.

7. TCP Header Explained

A TCP segment contains a header followed by application data. The header carries information required to manage the connection and data transfer.

The minimum TCP header size is 20 bytes. Options can make it larger, up to 60 bytes.

Important TCP header fields

Field Purpose
Source PortIdentifies the sending application endpoint.
Destination PortIdentifies the receiving application endpoint.
Sequence NumberIdentifies the sequence position of transmitted data.
Acknowledgment NumberIndicates the next sequence number expected.
Data OffsetIndicates the TCP header length.
Control FlagsInclude SYN, ACK, FIN, RST, PSH, URG, and other control bits.
WindowCommunicates the receiver's advertised window.
ChecksumHelps detect corruption in the TCP segment and its pseudo-header.
Urgent PointerUsed with the URG flag for urgent data signaling.
OptionsCarry optional capabilities such as MSS and window scaling.

Important TCP flags

  • SYN: Synchronizes sequence numbers and initiates connection establishment.
  • ACK: Indicates that the acknowledgment field is valid.
  • FIN: Indicates that the sender has finished sending data in that direction.
  • RST: Resets a connection.
  • PSH: Requests that data be pushed toward the receiving application without unnecessary delay.
  • URG: Indicates that the urgent pointer field is significant.
Packet analysis tip

When examining TCP traffic in Wireshark, look for SYN, SYN-ACK, and ACK packets. These are common indicators of a TCP connection handshake.

8. UDP Header Explained

UDP uses a compact header of only 8 bytes. It contains four fields, each 16 bits in size.

Field Size Purpose
Source Port16 bitsIdentifies the sending port; it may be zero when no reply port is needed.
Destination Port16 bitsIdentifies the destination application port.
Length16 bitsSpecifies the length of the UDP header and data.
Checksum16 bitsProvides error detection for the UDP datagram and IP pseudo-header.

UDP checksum note

For IPv4, the UDP checksum is optional at the protocol level. For IPv6, it is normally required, subject to defined exceptions. Modern UDP checksum behavior is described by the relevant standards.

The small header is one reason UDP is useful for applications that need a lightweight datagram transport.

9. Understanding Port Numbers

Port numbers identify application endpoints at the transport layer. TCP and UDP each have their own port-number space.

Port numbers are 16 bits long, giving a range from 0 to 65535.

10. Real-World Applications of TCP and UDP

Where is TCP commonly used?

  • HTTPS over TCP: Secure web communication using HTTP over TLS and TCP.
  • SSH: Secure remote command-line access.
  • FTP: Traditional file transfer communication.
  • SMTP: Email transfer between mail systems.
  • IMAP: Accessing and managing email messages.
  • Database connections: Many database protocols use TCP.

Where is UDP commonly used?

  • DNS: Many ordinary DNS queries use UDP.
  • DHCP: Uses UDP for address configuration exchanges.
  • VoIP: Real-time voice applications commonly use UDP-based media transport.
  • Online gaming: Many games use UDP for time-sensitive communication.
  • Streaming and real-time media: Some systems use UDP-based protocols.
  • NTP: Network time synchronization commonly uses UDP.

Can modern applications use UDP and still be reliable?

Yes. UDP itself does not provide TCP-style reliability, but protocols built on top of UDP can implement their own mechanisms.

For example, QUIC uses UDP as its transport substrate and provides features including reliable streams, congestion control, and secure connection establishment. HTTP/3 uses QUIC.

This is an important modern networking concept: choosing UDP does not necessarily mean an application must accept unreliable communication.

11. How Application Data Travels Through the Network

When an application sends data, the transport protocol adds its own header. The IP layer then encapsulates the transport data inside an IP packet.

TCP encapsulation

IP Header Source and destination IP addresses
TCP Header Ports, sequence number, ACK, flags, window
Application Data

UDP encapsulation

IP Header Source and destination IP addresses
UDP Header Source port, destination port, length, checksum
Application Data

The transport-layer protocol is identified in the IP header. For IPv4, the Protocol field uses value 6 for TCP and 17 for UDP. IPv6 uses the corresponding Next Header values for TCP and UDP.

At the receiving device, the IP layer processes the packet and passes the transport payload to the appropriate TCP or UDP implementation.

12. Performance, Latency, and Reliability

TCP and UDP are designed for different transport requirements. Neither is universally better. The appropriate choice depends on what the application needs.

When reliability is important

Consider transferring a file. If a portion of the file is lost, the application generally needs that missing data to be recovered. TCP provides built-in sequencing, acknowledgment, and retransmission mechanisms that support this requirement.

When timeliness is important

Consider a live voice conversation. Receiving an old audio packet several seconds late may be less useful than continuing with the current audio. A real-time application may prefer to tolerate some loss rather than wait for retransmission.

13. TCP and UDP Network Troubleshooting

Understanding transport protocols helps network engineers identify why an application cannot communicate with a remote service.

TCP troubleshooting

If a client cannot establish a TCP connection, investigate:

  • Whether the destination IP address is reachable.
  • Whether the server is listening on the expected TCP port.
  • Whether a firewall is blocking the connection.
  • Whether routing and return routing are correct.
  • Whether the server is responding with SYN-ACK or RST.
  • Whether retransmissions indicate packet loss or filtering.

UDP troubleshooting

UDP does not establish a TCP-style connection. Therefore, the absence of a handshake does not indicate a failure.

Investigate:

  • Whether the application is listening on the expected UDP port.
  • Whether firewalls permit UDP traffic in the required direction.
  • Whether the destination service is responding.
  • Whether the application is using the correct server and port.
  • Whether packet loss, routing, or network address translation is affecting traffic.

Useful Windows commands

netstat -ano netstat -an | findstr ":443" ipconfig /all tracert 8.8.8.8

Useful Linux commands

ss -tulnp ss -tn ip route ip addr sudo tcpdump -i any tcp port 443 sudo tcpdump -i any udp port 53

The ss command displays socket information. The tcpdump command captures traffic for inspection. Root or elevated privileges may be required.

14. Practical Lab: Observe TCP and UDP Traffic

Theory becomes easier to understand when you observe actual packets. This exercise uses Wireshark, a network protocol analyzer.

Lab requirements

  • A Windows or Linux computer.
  • Wireshark installed.
  • An active network connection.
  • Permission to capture traffic on the selected interface.

Part A: Capture TCP traffic

  1. Open Wireshark.
  2. Select the active network interface.
  3. Start packet capture.
  4. Open a website that uses HTTPS over TCP, if available.
  5. Stop the capture.
  6. Enter this display filter:
tcp

To inspect connection establishment, use:

tcp.flags.syn == 1

Look for SYN, SYN-ACK, and ACK packets. Examine the source and destination ports, sequence numbers, acknowledgment numbers, and TCP flags.

Part B: Capture UDP traffic

  1. Start a new capture.
  2. Generate some DNS traffic by looking up a domain name.
  3. Stop the capture.
  4. Use the following display filter:
udp

To inspect DNS traffic specifically, use:

udp.port == 53

Inspect the UDP source port, destination port, length, checksum status, and DNS message.

15. Frequently Asked Questions

1. Is TCP more reliable than UDP?

TCP provides built-in reliable, ordered delivery mechanisms. UDP does not provide those guarantees by itself. An application using UDP can implement additional reliability.

2. Is UDP always faster than TCP?

No. UDP has less built-in protocol overhead, but actual performance depends on the application, network conditions, and protocol design.

3. Does UDP use port numbers?

Yes. UDP uses 16-bit source and destination port fields to identify application endpoints.

4. Can TCP and UDP use the same port number?

Yes. TCP and UDP have separate port-number spaces. For example, DNS commonly uses both TCP port 53 and UDP port 53.

5. Why does TCP use a three-way handshake?

It synchronizes connection state and initial sequence numbers between the endpoints.

6. Does UDP guarantee packet delivery?

No. UDP does not guarantee delivery, ordering, or duplicate protection.

7. What is the minimum TCP header size?

The minimum TCP header is 20 bytes. Options can increase the size.

8. What is the UDP header size?

The UDP header is 8 bytes.

9. Does HTTPS always use TCP?

No. Traditional HTTPS commonly uses HTTP over TLS over TCP. HTTP/3 uses QUIC over UDP.

10. Which protocol should I learn first?

Learn both. Understanding TCP and UDP is essential for networking, Linux administration, security, troubleshooting, and network engineering.

16. Conclusion

TCP and UDP are two fundamental transport protocols that support application communication across IP networks.

TCP provides a reliable, ordered byte stream with connection management, flow control, and congestion control. UDP provides a lightweight datagram service with fewer built-in mechanisms and more responsibility left to the application.

As a networking learner, you should be comfortable identifying both protocols, understanding their headers, recognizing common port numbers, and examining their behavior in packet captures.
